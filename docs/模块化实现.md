# 模块化管理实现

当前 CLI 的模块能力已经通过独立的 `module` 命令分支暴露出来，命令行入口与之前的旧用法并不一致。本文档基于当前代码实现说明模块的真实命令和行为。

## 1. 模块命令入口

当前实现中，模块相关能力主要由以下三个子命令提供：

```pwsh
perigon module list
perigon module install <PackagePath|OfficialPackageName> <ServiceName>
perigon module pack <ModuleName> <ServiceName>
```

其中：

- `module list`：查看官方模块列表。
- `module install`：安装本地 zip 包或官方模块包。
- `module pack`：打包当前模块为可安装的 zip 包。

> 代码中并没有注册根级 `perigon install` 命令；实际入口是 `perigon module ...`。

## 2. 官方模块来源

官方模块元数据和包文件来源于 GitHub 上的 [Perigon.Modules](https://github.com/AterDev/Perigon.Modules) 仓库：

- `modules.json`：存储官方模块元数据，包括模块名、版本、作者、描述等。
- `package_modules/`：存放已打包的模块 zip 文件。

## 3. 当前实现说明

### 3.1 查看官方模块列表

执行：

```pwsh
perigon module list
```

实际流程是：

1. 先请求 `https://api.github.com` 检查是否可以访问 GitHub。
2. 如果可以连接，则读取 `Perigon.Modules` 仓库中的 `modules.json`。
3. 将模块信息按名称排序后显示为表格，包含：模块名、版本、作者、描述。

如果没有读取到任何模块信息，会提示“当前没有官方模块可用”。

### 3.2 安装官方模块

当安装参数以 `Perigon.` 前缀开头时，会被识别为官方模块：

```pwsh
perigon module install Perigon.SystemMod AdminService
```

实际流程是：

1. 识别包名是否为官方模块名（通过 `Perigon.` 前缀判断）。
2. 解析模块名并从官方仓库下载对应 zip 包。
3. 下载后的 zip 包会进入临时目录，随后复用现有的本地包安装流程继续安装。

### 3.3 安装本地模块包

也支持安装本地 zip 包：

```pwsh
perigon module install ./package_modules/FileManagerMod.zip AdminService
```

实际流程是：

1. 校验给定路径对应的 zip 文件存在。
2. 读取模块包内容并提取模块源码。
3. 将模块复制到当前解决方案的 `src/Modules` 目录下。
4. 自动更新解决方案文件、目标服务的项目引用和全局 `using`。

### 3.4 打包模块

打包命令用于把现有模块打成安装包：

```pwsh
perigon module pack FileManagerMod AdminService
```

执行后会生成一个 zip 包并放置到解决方案根目录下的 `package_modules` 目录中，便于后续安装或分发。

## 4. 实现细节

### 4.1 数据获取

当前实现中，官方模块数据获取依赖以下几个步骤：

- 使用 GitHub API 检查可用性；
- 通过 GitHub 仓库 tree API 查找 `modules.json`；
- 读取对应 blob 内容并反序列化为模块元数据；
- 使用 `raw.githubusercontent.com` 下载官方模块的 zip 包。

### 4.2 安装前置条件

模块安装并不是纯粹“复制文件”这么简单，当前实现还会做以下检查和调整：

- 目标服务目录必须存在；
- 当前目录必须处于有效解决方案上下文中；
- 安装成功后会为目标服务添加模块项目引用；
- 会更新服务目录下的 `GlobalUsings.cs`，让模块命名空间可直接被服务代码使用。

## 5. 结论

当前模块化能力已经从旧的单一 `install` 入口演进为更明确的 `module` 子命令体系。与旧文档相比，实际行为更接近下面这条结论：

- 通过 `module list` 查看官方模块；
- 通过 `module install` 安装本地或官方模块；
- 通过 `module pack` 生成模块安装包。
